# APEX maintainer clinics

Work with a willing maintainer on one issue. APEX does not find consenting participants, contact projects, flood repositories with PRs or claim acceptance on their behalf.

1. Agree the issue, participants, time/expense limit and acceptance evidence. Use `/clinic` to record the human's consent attestation and link to an existing GitHub issue. Names are self-declared; no invitations are sent.
2. Inspect contribution instructions in Plan. Use `/packet` to preview selected context and `/task` to agree ownership, files, acceptance criteria and a finite allowance. Private keys and unrelated chats stay local.
3. Implement only after switching to Build and approving relevant actions. Use meaningful reproduction and validation. Keep actual shell/tool receipts separate from model-written conclusions.
4. Review the patch with the maintainer. Push, issues and PR publication require separate authorization. Passing tests is not maintainer acceptance.
5. Build a selected `/receipt`. Record an outcome in `/clinic` with its receipt and same-repository review link. Status is the human's attestation, not an independently fetched GitHub result. Keep rejection and limitations as evidence too.
6. Ask willing participants whether the context was useful, what confused them, whether credit is accurate and whether they would use it again. Record voluntary feedback without secrets. `/credit` attribution needs the credited room member's approval before receipt inclusion.

There are no completed real-project clinics bundled with APEX. Package/fixture checks demonstrate workflow plumbing, not adoption, model quality, accepted contributions, customer growth or sponsorship income.

Original inert recipes: `/plugin install apex-dev@apex-official`. Inspect `/recipes` before invoking a skill. Recipe contracts and user-outcome records are separate; a fixture is not a real maintainer outcome.
